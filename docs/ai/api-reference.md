# SDK and platform API reference

Signatures and semantics of everything a module uses. The source of truth is the code:

- `packages/sdk/src/manifest.ts` (manifest);
- `packages/sdk/src/server.ts` (`ModuleContext` and server types);
- `packages/sdk/src/web.tsx` (web SDK);
- `packages/ui/src/components/*` (UI kit);
- `packages/contracts/src/*` (shared DTOs).

Names declared by existing modules are in [reference.md](reference.md).

## 2. `ModuleContext` (server)

Every route, handler, job, AI tool, resolver and seed receives `ctx`. Members:

### Core

| Member                                               | Semantics                                                                                                                                                          |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ctx.module`                                         | your manifest                                                                                                                                                      |
| `ctx.db`                                             | Drizzle (node-postgres) on the platform database                                                                                                                   |
| `ctx.transaction(fn: (tx) => Promise<T>)`            | runs `fn` in a transaction; pass `{ tx }` to `audit`, `events`, `notifications`, `records`, `portal`, `forms`                                                      |
| `ctx.principal()`                                    | current actor (`{ type: 'user'\|'service'\|'system'\|'ai_agent', id, name, onBehalfOf? }`) from async context                                                      |
| `ctx.isEnabled()`                                    | whether your module is enabled                                                                                                                                     |
| `ctx.logger`                                         | pino logger tagged with the module id (never log secrets or personal data)                                                                                         |
| `ctx.audit.record(entry, { tx?, principal? })`       | `entry = { action, entityType?, entityId?, entityLabel?, changes?, metadata?, outcome?: 'success'\|'failure'\|'denied', category?: 'data'\|'security'\|'system' }` |
| `ctx.audit.diff(before, after, fields?)`             | `{ field: [before, after] }` for changed keys (secrets redacted by name)                                                                                           |
| `ctx.events.publish(name, payload, { tx? })`         | transactional outbox; delivered after commit to every module that `consumes` it                                                                                    |
| `ctx.jobs.enqueue(name, data, { delayMs?, jobId? })` | queues one of your `jobs` (dedupe with `jobId`); the job's declared `attempts`/`backoffMs` apply                                                                   |
| `ctx.settings.get<T>(key)` / `all()`                 | admin-edited setting or the manifest default                                                                                                                       |
| `ctx.rbac.permissionsFor(userId)`                    | another user's effective `PermissionSet`                                                                                                                           |

Task handlers receive `task: { runId, jobId, attempt, scheduledFor, timeZone?, lastSuccessAt, timeoutMs?, signal, log(message, level?) }`
and return `{ summary?, summaryParams?, metrics?, href? }` (`summary`: an i18n key in the module's catalog shown in the
reader's language with `summaryParams`, or short plain text). To fail, throw: Scheduled jobs explains the failure from
its code with `runProblemOf(err, hints)` (`@isbp/sdk`: database, HTTP, sandbox and remote-system errors → a
`RunProblem { kind, params, connection? }` the UI words in three languages); put a `RunProblem` in
`details.problem` when the task knows better (which connection failed). Sync adapters' `write` takes
`expectedUpdatedAt` (409 `CONFLICT`, `details.reason: 'changed'` when the record moved on since it was read).

### Phase 5: sync adapters and connectors (Integrations Hub)

Types are in `packages/sdk/src/integrations.ts`; the design is `docs/architecture.md` §12. Data modules provide
**adapters**, connector modules provide **connectors**, and the `integrations` module maps between them. A module
normally implements one side and never calls these services itself; the hub does.

| Member                                                                        | Semantics                                                                                                                                                                                                                                                          |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ctx.sync.entities(auth?)`                                                    | `{ entity, moduleId, name, icon, permission, container, comments, recordType, matchKeys }[]` of enabled modules (filtered by permission)                                                                                                                           |
| `ctx.sync.fields(entity, { containerId? })`                                   | the adapter's field catalogue: `{ key, label, type, choices?, required?, readOnly?, createOnly?, maxLength? }[]`                                                                                                                                                   |
| `ctx.sync.read/readMany/list/findBy(entity, …)`                               | `SyncRecord { id, ref, title, href, updatedAt, containerId, values }`; `list` is update-ordered and cursor-paged; `findBy` matches on the adapter's `matchKeys` (null when none or ambiguous)                                                                      |
| `ctx.sync.write(entity, { id?, containerId?, values }, { auth, tx, source })` | 403 without the entity's `permission`; 422 `VALIDATION_FAILED` for unknown, read-only, create-only (on update), invalid-choice or missing required fields — then the adapter writes in `tx`. Returns `{ id, record }`: the record as stored, read in the same `tx` |
| `ctx.sync.comments.list/add(entity, id, …)`                                   | comment sync for entities with `commentEvents`                                                                                                                                                                                                                     |
| `ctx.connectors.list()` / `validate(type, config, secrets)`                   | `{ type, moduleId, name, configSchema, secretsSchema, secretKeys, objects[{ type, name, entities, capabilities, scoped }] }[]`; validation 400 with `issues`                                                                                                       |
| `ctx.connectors.open(type, { id, config, secrets })`                          | an `OpenConnector`: `test`, `scopes`, `fields`, `changes`, `get`, `create`, `update`, `comments`, `webhook`, `defaultMapping`; 409 `NOT_SUPPORTED` for capabilities the object type lacks                                                                          |
| `defineServerModule({ onSyncChange(change, ctx) })`                           | receives every event a sync entity lists (`{ entity, id, kind: 'record'\|'comment', event }`), in the worker                                                                                                                                                       |
| `defineServerModule({ frameAncestors(path, ctx) })`                           | websites (`https://host[:port]`) that may frame your public page `/p/<id><path>`; asked by the web proxy (cached 30 s); default none                                                                                                                               |

**Writing an adapter** (`defineServerModule({ sync: { [entity]: SyncAdapter } })`): `fields`, `read`, `readMany`,
`list`, `write`, `idFromEvent`, optional `findBy` + `matchKeys` and `comments`. `write` runs **in the hub's `tx`**,
through your own write logic, publishing your usual events with `{ tx }` and auditing with `source` in the metadata.
Refuse what your UI would refuse, including statuses that need an approval (409 `INVALID_TRANSITION`,
`details.reason: 'approval_required'`). Value shapes: `user` = local user id, `parent` = local record id, `date` =
`YYYY-MM-DD`, `datetime` = ISO, `tags` = `string[]`, empty = `null`.

**Writing a connector** (`defineServerModule({ connectors: { [type]: ConnectorHandler } })`): every call gets
`conn: { connectionId, config, secrets, http, databases, cache, signal }`. `conn.http` only reaches `hosts(config)` (private
addresses allowed for them; link-local/metadata never) and refuses plain `http://` with 422 `INSECURE_HTTP` unless
the connection allows insecure HTTP (`open(type, { …, allowInsecureHttp })`; loopback is always allowed). Keep OAuth tokens in `conn.cache`. `changes()` returns
records oldest first with an opaque cursor that never skips equal timestamps. `RemoteRecord.version` drives
optimistic concurrency (`update(…, { expectedVersion })` → 409 `REMOTE_CONFLICT`). Map failures to 502
`REMOTE_AUTH_FAILED`, 429 `REMOTE_RATE_LIMITED` (`details.retryAfterSeconds`), 422 `REMOTE_REJECTED`
(`details.message`). `webhook()` only says which records changed. Users are `{ email, name, id? }`. Leave a field
out of `RemoteRecord.values` when the API didn't return it (it is then unknown, not empty). `defaultMapping` value
maps may give each row a `direction` (`both`, `pull`, `push`) for many-to-one maps; at most one row per remote
value may pull and one per ISBP value may push (`integrations-defaults.test.ts` checks every connector). Contribute the
settings form as the web slot `integrations.connector-config.<module>.<type>` (`ConnectorConfigSlotProps`).

Database connectors declare `databaseConnections(config): string[]`. `conn.databases.get/query` only accept
those IDs, require enabled, read-only connections with purpose `data`, and force read-only Data queries.
No credentials, procedures or writers are exposed. Catalogue entries include `transport: 'http' | 'database'`
and optional `configurePermission` (declared on the manifest connector); the hub enforces that permission for
source creation, edits, deletion, tests and secret rotation. SQL Server sources must use a SELECT-only login.
Core's `core.hr-database` connector and `core.person` / `core.department` adapters are the directory example;
see `apps/api/src/core/hr-sync/README.md`.

### Phase 6: customisation kinds, change sets and MCP

Types are in `packages/sdk/src/customizations.ts`; the design is `docs/architecture.md` §13. A module that owns a
configurable surface provides a **kind**; the `assistant` module turns proposals into change sets that a person
applies; the MCP server (`POST /api/v1/mcp`) exposes the tool registry and the kinds to outside agents.

| Member                                                                                            | Semantics                                                                                                                                                                                                                                                                                                 |
| ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

**Writing a kind** (`defineServerModule({ customizations: { [kind]: CustomizationHandler } })`): `schema` (the
admin API's create schema without status flags, with `.describe()` texts), `guide`, `list`, `get`, optional `check`
and `templates`, and `apply({ op, id, value }, ctx, auth)` with your own service, constructed with the `ctx` you
receive. `op` is `create`, `update`, `archive`, `restore` or `delete`; `value` is set for create and update. Throw
the same `HttpError`s as your routes. See recipe 23. A template's `build` may return `ref` and `before:
(TemplateProposal & { kind })[]` — changes of other kinds proposed first in the same change set, which the template's
own value refers to as `"$ref:<ref>"` (the change set renames refs it already uses). `get` may return `links`, shown on
the applied change set and in the agent's apply result.

**Change-set packages** (`ChangeSetPackage` in `@isbp/sdk`; zod `changeSetPackageSchema` in
`@isbp/module-assistant/contracts`): `{ format: 'isbp.change-set-package', version: 1, key?, title: LocalizedText,
summary?, requires?: { modules? }, items: ProposeItem[] }` (≤ 300 items, `MAX_PACKAGE_ITEMS`; `$ref:<ref>` to earlier
items). `GET /assistant/change-sets/:id/export` downloads a change set as one (`<reference>.json`);
`POST /assistant/change-sets/import` (body ≤ 4 MB) and `POST /assistant/packages/:module/:key/install` create a draft
change set from one, checking every item as a proposal and creating nothing when one fails (400 `PACKAGE_UNSUPPORTED`
with `missingModules`/`unknownKinds`, 403 for kinds the person can't read, 422 `VALIDATION_FAILED` with `issues` at
`items.<index>.<field>`); `GET /assistant/packages` lists the built-in ones. See recipe 28.

## 3. Authorization: `AuthContext` and route config

`req.auth` (routes), the `auth` argument (resolvers, tools), `ctx.ai.agent()`:

| Member                           | Semantics                                                                                      |
| -------------------------------- | ---------------------------------------------------------------------------------------------- |
| `principal`, `user`, `client`    | who is calling (`user` is null for API clients and agents; `client` set for API clients)       |
| `can(permission, resource?)`     | `resource = { departmentId? }` or `{ recordType, recordId }`; without `resource`: global grant |
| `require(permission, resource?)` | throws 403 and audits the denial                                                               |
| `reach(permission)`              | `{ global, departmentIds, records: [{ type, id }] }` — build list filters from it              |
| `permissions.hasAny(p)`          | holds `p` at any scope                                                                         |

Route `config`:

- `permission`: a string or string[] (all required).
- `scoped: true`: any scope passes the guard, and you check the scope.
- `public: true`: no session.
- `csrf: false`: skips the CSRF check (only for flows that carry their own proof).
- `rateLimit: { max, timeWindow }`.

Patterns in roles: `*`, `<id>.*`, `<id>.<resource>.*`.
