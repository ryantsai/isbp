| ナレッジ管理                       | ユーザーが自分で使える回答を作成し、レビューする                                 | **ナレッジ**、**ナレッジ → 記事の管理**                                                           | ナレッジ編集者、担当者                                                |

| 変更実現                           | 変更を評価、承認、スケジュールし、競合を避ける                                   | **サービス デスク → 変更**、**承認**での CAB の承認                                               | 変更マネージャー、CAB                                                 |
| リリース管理とデプロイ管理         | バージョンを計画し、準備状況を確認し、デプロイを記録し、デリバリーを測定する     | **アプリケーション → アプリケーション**、**アプリケーション → リリース カレンダー**               | アプリケーションのオーナー、リリース マネージャー、CI/CD パイプライン |
| サービス構成管理                   | サービスやサーバーと、それらの依存関係を把握する                                 | **構成アイテム** (CMDB)                                                                           | CMDB マネージャー、担当者                                             |
| IT 資産管理                        | ハードウェア、ライセンス、契約、ベンダーを発注から廃棄まで追跡する               | **資産** (**ハードウェア**、**ソフトウェア**、**契約**、**ベンダー**)、**マイ デバイス**          | 資産マネージャー、契約マネージャー                                    |
| ID とアクセスの管理                | ユーザーのオンボーディングとオフボーディングを行い、アクセスを付与、レビューする | **管理 → ユーザー**、**グループ**、**ロールとアクセス**、**アプリケーション**。**アクセスの申請** | ID 管理者、人事担当者、承認者                                         |
| プロジェクトとポートフォリオの管理 | IT プロジェクトを運営し、誰が何に取り組んでいるかを把握する                      | **プロジェクト → プロジェクト**、**プロジェクト → マイ タスク**                                   | プロジェクト マネージャー、プロジェクト チーム                        |

| 既存ツールとの連携                 | ServiceDesk Plus と Azure DevOps Server を ISBP と同期させる                     | **管理 → 統合**                                                                                   | 統合管理者                                                            |

## 共通の構成要素

ISBP のすべての領域は同じ部品で構成されているため、1 か所で覚えれば、どこでも同じように使えます。

| 構成要素             | 意味                                                                                                                                                                                                                                                                                                                                         |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 申請と承認           | 判断が必要なもの (アクセス、購入、変更、廃棄、プロジェクト提案、データベース ロール、変更セット) は、すべて承認**ワークフロー**を経由します。承認者は 1 つの承認一覧 (**承認**) で判断し、申請者は**承認ルート**を確認できます。管理者は**管理 → ワークフロー**でワークフローを設計します。                                                  |
| 通知                 | ヘッダーのベルのほか、メール、Microsoft Teams、Slack、Webhook で届きます。アプリ内とメールのそれぞれで受け取る通知を、種類ごとに選択できます (**プロファイルと設定 → 通知**)。通知の文面は自分の言語で書かれます。                                                                                                                           |
| レコードとリンク     | チケット、変更、資産、構成アイテム、リリース、タスクなどのレコードは、**関連レコード**パネル (**レコードをリンク**) で、領域をまたいで相互にリンクできます。表示されるのは、開くことが許可されているリンク先のレコードだけです。                                                                                                             |
| 添付ファイル         | スクリーンショット、契約書、文書は、レコードの**添付ファイル**パネルに追加します。ファイルは保存される前にチェックされます。                                                                                                                                                                                                                 |
| カスタム フィールド  | 管理者は、**管理 → カスタム フィールド**で、ユーザー、グループ、部署、モジュールのレコードに独自のフィールド (コスト センター、影響を受ける拠点など) を追加します。フォームも同じ種類のフィールドを使用します。                                                                                                                              |
| ロールとアクセス許可 | 表示できる内容と実行できる操作はロールによって決まります。ロールは自分または自分のグループに付与され、部署や 1 つのレコードに限定されることも、期限付きのこともあります。**プロファイルと設定 → 自分のアクセス権**で自分のロールを確認できます。                                                                                             |
| 監査ログ             | すべての変更、サインイン、アクセスの判断は**管理 → 監査ログ**に記録され、編集することはできません。                                                                                                                                                                                                                                          |
| AI とアシスタント    | **IT に質問**は、ナレッジ ベースから従業員の質問に回答します。**ヘルプデスク AI** は、担当者のトリアージと返信を支援します。ヘッダーの**アシスタント**は、どのページでも一緒に作業し、構成の変更を変更セットとして準備します。いずれも自分のアクセス許可の範囲で動作し、データがプラットフォーム外に送信される前に個人データをマスクします。 |

## シナリオ: 新入社員が月曜日に入社する

来週、営業部門に新しい同僚が入社します。人事がアカウントを作成し、マネージャーがノート PC を発注してアクセスを申請し、新入社員は初日にサインインします。

関係者: 人事担当者 (デモでは、営業部門のユーザーを管理する `hr.partner`)、新入社員のマネージャー、承認者、サービス デスク、資産マネージャー。

1. 人事担当者が**管理 → ユーザー**を開き、**ユーザーを追加**を選択して、プロファイル (部署、上司) を入力し、**開始時の状態**で**事前登録**を選択します。アカウントは作成されますが、まだサインインはできません。[管理者](administrators.md)を参照してください。
2. マネージャーがノート PC を発注します。**申請 → PC・機器の申請**で**他の人のための申請**をオンにし、**誰のためですか？** で対象者を選択して、**送信**を選択します。フォームの承認は**承認**で行われ、承認された申請はサービス デスクのチケットになります。[機器やソフトウェアを申請する](employees.md#フォームで機器やソフトウェアを申請する)を参照してください。
3. マネージャーは初日の前にアクセスを申請します。**申請 → アクセスの申請**で、ロール (例: **Finance ERP** のロール) を選択し、**誰が必要としていますか？** → **他の人**で新入社員 (**事前登録**と表示されます) を選び、期間と理由を入力して、**申請を送信**を選択します。確認ステップに、誰が承認するかが表示されます。[アクセスを申請する](employees.md#アプリケーションやロールへのアクセスを申請する)を参照してください。
4. 承認者が**承認**で判断します。[申請を承認または却下する](employees.md#申請を承認または却下する)を参照してください。最後の承認が完了すると、ロールが終了日付きで自動的に付与されます。付与されたロールは、その人がオンボーディングされた時点で有効になります。
5. 初日に、人事担当者がユーザーのページで**オンボーディング**を選択します。新入社員はサインインできるようになり、アクセスもすぐに使えます。付与されたアクセスは本人の**プロファイルと設定 → 自分のアクセス権**に表示され、誰がどのロールを持っているかを (ロール クエリ API を通じて) ISBP に問い合わせる業務アプリケーションにも付与が反映されます。
6. 資産マネージャーが、**資産 → ハードウェア**で**在庫**のノート PC を選び、**割り当て**を選択して新入社員を選択します。ノート PC は**使用中**になり、新入社員の**マイ デバイス**に表示されます。続いて担当者がチケットで**完了**を選択します。[資産](assets.md)を参照してください。最初の 1 週間のその他の作業は、**ナレッジ**の **New joiner IT checklist** 記事で説明しています。

> **注:** アクセスは、有効なユーザーと事前登録されたユーザーについて申請できます。一時停止中またはオフボーディング済みのユーザーについての申請は拒否されます。申請が承認待ちの間にユーザーが一時停止またはオフボーディングされた場合、申請は**付与できませんでした**で終了し、何も付与されません。

> **ヒント:** 退職者が出たときは、そのユーザーのページで**オフボーディング**を選択すると、サインインが無効になり、セッションが終了します。グループとロールを削除することもでき、他の領域にも通知されるため、たとえばデータベースのアカウントも削除されます。

## シナリオ: 「VPN が何度も切れる」

在宅勤務の従業員の VPN が数分おきに切断されます。ほとんどの場合はナレッジ記事で解決し、解決しない場合はサービス デスクが対応します。その解決策が、次の回答の質を高めます。

関係者: 従業員、IT に質問、サービス デスク担当者 (デモでは `helpdesk`)、ネットワーク チーム。

1. 従業員が **IT に質問**を開き、「VPN が何度も切断される」と入力します。IT に質問はナレッジ ベースから回答し (デモでは **VPN disconnects every few minutes** から)、**参照元**にその記事を表示します。
2. 手順で解決した場合、従業員は**解決しました**を選択します。チケットは不要です。解決しない場合は、**まだ解決しません**、**チケットを確認**、**チケットを作成**の順に選択します。[IT に質問](employees.md#チケットを登録する前に-it-に質問する)を参照してください。
3. インシデントが**サービス デスク → チケット**に表示されます。ヘルプデスク AI がカテゴリ (VPN)、割り当てグループ、優先度を提案し、解決済みの類似チケットを表示します。SLA タイマーが開始されます。
4. 担当者は、チケットが既知のエラー **VPN client 5.2 crashes on macOS 15** (**サービス デスク → 問題**にある問題) に該当することに気付き、その回避策を適用してチケットを解決します。[サービス デスク](service-desk.md)を参照してください。
5. 従業員に通知が届きます。従業員はチケットを開いて**はい、クローズします**を選択し、サービスを評価します。[解決を確認する](employees.md#解決を確認してサービスを評価する)を参照してください。
6. 解決策がまだナレッジ ベースにない場合、担当者はチケットから記事の下書きを作成し、編集者がそれをレビューして公開します。これで、次に同じ質問をした人に IT に質問が回答できるようになります。

## シナリオ: 60,000 TWD を超えるノート PC

ノート PC の申請は部門長が承認し、60,000 TWD を超える場合は IT 資産管理も承認します。承認された申請はサービス デスクが処理し、最終的に申請者に割り当てられた資産になります。

関係者: 従業員、その部門長、資産マネージャー、サービス デスク担当者。

1. 従業員が**申請**を開き、**ノート PC の申請**を選択して、**モデル**を選び、**見積額 (TWD)** (たとえば 72,000) と**必要な理由**を入力して、**送信**を選択します。[機器やソフトウェアを申請する](employees.md#フォームで機器やソフトウェアを申請する)を参照してください。
2. 最初に**部門長の承認**が行われます。金額が 60,000 TWD を超えているため、続いて資産マネージャーが判断する **IT 資産管理**のステップがあります。どちらも**承認**で判断します。
3. 承認されると、申請はサービス デスク向けの**ハードウェア › ノート PC** カテゴリのサービス要求チケットになります。申請者の申請ページには**対応中**と **SR-… を開く**が表示されます。
4. 資産マネージャーが**資産 → ハードウェア**で在庫のノート PC を割り当て (**割り当て**)、**関連レコード**でその資産をチケットにリンクします。
5. 担当者がチケットで**完了**を選択します。申請ページに**完了**と表示され、ノート PC が従業員の**マイ デバイス**に表示されます。

> **ヒント:** デモでは、この仕組み全体 (承認ワークフロー、フォーム、サービス カタログ項目) がアシスタントを使って変更セット `CS-00001` として作成されています。[アシスタントでプロセスを変更する](#シナリオ-アシスタントでプロセスを変更する)を参照してください。

## シナリオ: 本番環境へのリリース

Finance ERP チームは、バージョン 12.1 へのアップグレードを進めています。作業はプロジェクトで計画し、バージョンはリリースとして追跡します。本番環境には CAB が承認した変更が必要で、デプロイはパイプラインが記録します。

関係者: プロジェクト マネージャーとチーム、アプリケーションのオーナーまたはリリース マネージャー、変更マネージャーと CAB、CI/CD パイプライン。

1. **プロジェクト → プロジェクト**の **ERP upgrade to v12** プロジェクトに、**Change request for the production cutover** というタスクがあります。[プロジェクト](projects.md)を参照してください。
2. リリース マネージャーが**アプリケーション → アプリケーション**で **Finance ERP** を開き、**リリース**、**12.1.0 (ERP v12 upgrade)** の順に開きます。**本番の準備状況**には、**承認済みの変更がリンクされている**、**テストまたはステージングで成功**、**リリース ノートが記述されている**、**本番デプロイの失敗なし**のチェックが一覧表示されます。
3. リリースには変更が必要です。デモでは、下書きの **Deploy Finance ERP 12.1.0 to production** がすでにあります。ない場合は、変更マネージャーがリリースで**変更を起票**を選択します (**変更マネージャー** (Change manager) ロールのないリリース マネージャーには表示されません)。新しい変更が、そのタイトルで、リリースにリンクされた状態で**サービス デスク → 変更**に開きます。変更マネージャーは変更計画 (変更の種類 (**通常**)、リスク、予定期間、実施計画、切り戻し計画、テスト計画) を完成させ、**承認を申請**を選択します。[変更とリリース](changes-and-releases.md)を参照してください。
4. **変更の承認**ワークフローは、まず**変更マネージャー**に承認を求め、リスクが高い場合または重要な構成アイテムがかかわる場合は、続いて**変更諮問委員会 (CAB)** に承認を求めます。変更は **CAB 承認待ち**、続いて**スケジュール済み**になります。
5. プロジェクト マネージャーが**関連レコード**で変更をプロジェクトのタスクにリンクします。これで、本番切り替えの進捗をプロジェクトで確認できます。
6. 変更期間中に、パイプラインがデプロイを行い、API を通じて ISBP にデプロイを記録します (**CI/CD パイプライン** (CI/CD pipeline) ロールを持つ API クライアント)。ISBP は変更ポリシーを確認します。本番環境へのデプロイには、CAB が承認し、その予定期間内にある変更が必要です。それがない場合、オーバーライドを許可されたユーザーが理由を入力しない限りデプロイは拒否され、オーバーライドは監査されます。
7. リリース マネージャーがリリースを**リリース済み**に移動します。アプリケーションの**デリバリー メトリック** (デプロイ頻度、変更のリードタイム、変更失敗率、サービス復旧時間) にデプロイが反映されます。

## シナリオ: ERP のデータ フィード

財務部門は売上の数値を 4 時間ごとにデータ ウェアハウスに取り込みたいと考えており、レポート チームは ERP のデータを API として利用したいと考えています。フィードが失敗した場合は、その所有者に通知されます。

関係者: データベース接続管理者、データ エンジニア、ジョブの所有者と所有グループ (デモでは DBA チーム)。

1. データベース接続管理者が、**管理 → データベース接続**に ERP データベースを登録します (デモでは **Contoso ERP (reporting)** と **Contoso data warehouse**)。資格情報は暗号化され、用途は**データ**です。[データと自動化](data-and-automation.md)を参照してください。
2. データ エンジニアが、**データ API と ETL → データ API** で、パラメーター付きの SQL からデータ API を公開し (デモでは **Customers by region**)、テストして、呼び出しを許可する API クライアントを設定します。
3. 続いて、**データ API と ETL → パイプライン**で、ERP からウェアハウスに行をコピーするパイプラインを作成します (デモでは **Daily sales to warehouse**)。
4. **スケジュール ジョブ → ジョブ**のスケジュール ジョブがパイプラインを実行します (デモでは **Sales to warehouse (every 4 hours)**)。再試行が設定され、**実行が失敗したら所有者と所有グループに通知する**がオンになっています。
5. 最後の再試行の後も実行が失敗すると、所有者に通知 (**自分のジョブの実行が失敗したとき**) が届き、所有者は**スケジュール ジョブ → 実行履歴**で実行のログを開きます。デモでは、MySQL サーバーに接続できないため **CRM accounts to warehouse** が失敗します。失敗が繰り返されると、誰かが原因を修正して再び有効にするまで、ジョブは無効になります。

## シナリオ: 開発者のデータベース アクセス

開発者が、バグを調査するために ERP のレポート用データベースを 2 週間読み取る必要があります。誰かとパスワードを共有することなくアカウントを取得でき、アクセスは自動的に終了します。

関係者: 開発者、その上長、ロールの所有者、情報セキュリティ (高リスクのロールの場合)、DBA、レビュー担当者。

1. 開発者が**申請 → データベース アクセスを申請**を開き、ロール (デモでは **Contoso ERP (PostgreSQL)** の **ERP レポート (読み取り専用)**)、終了日、理由を選択して送信します。[データベース アクセスを申請する](employees.md#データベース-アクセスを申請する)を参照してください。
2. **上長の承認**、続いて**ロール所有者の承認**、高リスクのロールでは**情報セキュリティの承認**の各ステップの承認者が、**承認**で判断します。
3. ISBP がアカウントを作成し、データベース サーバーでロールを自動的に付与します。
4. 開発者に**アクセスの準備ができました**という通知が届きます。開発者は**データベース アクセス → 自分のデータベース アクセス**を開き、**パスワードを表示**を選択します (表示は 1 回限りです)。
5. 終了日の数日前に、開発者にリマインダー (**… のアクセスの期限が近づいています**) が届き、延長を申請できます。終了日になると、ロールは自動的に削除されます。
6. レビュー担当者は定期的に**データベース アクセス → アクセス レビュー**を確認し、アクセスごとに**維持**または**取り消し**を選択します。DBA は ISBP 以外で付与されたアクセス (**管理外のアクセス**) も確認でき、それを管理下に取り込むことができます。[データと自動化](data-and-automation.md)を参照してください。

## シナリオ: ServiceDesk Plus や Azure DevOps Server と併用する

一部のチームは、引き続き ManageEngine ServiceDesk Plus と Azure DevOps Server (どちらもオンプレミス) で作業しています。ISBP はレコードを双方向に同期し、その間も ISBP 自身のルール (承認、変更ポリシー) が適用されます。

関係者: 統合管理者、サービス デスク担当者、プロジェクト チーム。

1. 統合管理者が、**管理 → 統合**で各システムに接続します (デモでは **Contoso ServiceDesk Plus** と **Contoso Azure DevOps Server**)。[統合](integrations.md)を参照してください。
2. 同期プロファイルでは、何を同期するか、どの方向に同期するか、フィールドをどうマッピングするかを指定します。デモでは、ServiceDesk Plus との間に **Requests ↔ tickets**、**Problems → tickets**、**Changes → changes**、**Assets ↔ assets**、**Solutions → knowledge** が、Azure DevOps Server との間に **Team projects → projects**、**ERP work items ↔ tasks**、**Network work items → tasks** があります。
3. 同期されたレコードでは、**同期先**カードにリモートのレコードと前回の同期日時が表示されます。**今すぐ同期**を選択すると最新の状態に更新されます。
4. 同じフィールドが両方で変更された場合、プロファイルによっては人に判断を求めます。競合は**管理 → 統合 → 同期の競合**で待機し、管理者が **ISBP の値を保持**、**… の値を保持**、**両方をそのまま保持**のいずれかを選択します。
5. 他のシステムで行われた変更にも、ISBP のルールが適用されます。デモでは、ServiceDesk Plus で廃棄された資産は、ISBP の廃棄の承認を待ちます。

## シナリオ: アシスタントでプロセスを変更する

サービス デスクは、すべてのチケットで影響を受ける拠点を記録したいと考えています。リーダーがアシスタントに要件を伝え、管理者がレビューします。誤りがあった場合は、1 回の操作で元に戻せます。

関係者: サービス デスクのリーダー (デモでは `helpdesk`)、レビューして適用する管理者。

1. リーダーがヘッダーの**アシスタント**を開き、台北本社、新竹、東京を選択肢とする選択フィールド「影響を受ける拠点」をチケットに追加するよう依頼します。AI チャット モデルがない場合は、**カスタム フィールド**のガイド付きテンプレートが同じ質問をします。
2. アシスタントが変更セットを準備します。変更セットには、何が変わるか、読みやすい差分、セット全体を保存せずに試す**ドライ ラン**が含まれます。この時点では、まだ何も反映されていません。
3. リーダーにはカスタム フィールドを変更するアクセス許可がない (提案だけができる**構成閲覧者** (Configuration viewer) ロールを持っている) ため、**レビューを依頼**を選択します。デモでは、これが `CS-00002` で、管理者の**承認**で待機しています。
4. 管理者が**承認** (**変更セットのレビュー**) で変更セットをレビューし、承認します。承認すると、承認者のアクセス許可で、1 つのトランザクションで変更セットが適用されます。
5. 誤りがあった場合は、必要なアクセス許可を持つユーザーが**管理 → 変更セット**で変更セットを開き、**ロールバック**を選択します。その後に同じ構成が誰かによって変更されている場合、ISBP はロールバックを拒否し、先に最新の情報に更新して差分を確認するよう求めます。

[アシスタントと AI](assistant-and-ai.md)を参照してください。
